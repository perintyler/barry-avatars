I · The Setup

The Container Insight

Agents live in a container No direct access to the outside world besides tools

In production, Barry’s agents run in containers. They can’t touch the filesystem, make network requests, send Slack messages, or do anything else directly. The only way they interact with the outside world is through MCP tools served from the host.

If a tool doesn’t exist, the agent can’t do it. We don’t need to monitor and block bad behavior — we just don’t give the agent the tools to misbehave in the first place.

II · The Model

Traits & Scopes

Every task has traits and optionally a scope. Traits are what you give the agent — capability bundles. A task with debug gets Sentry and Datadog tools. A task with slack gets messaging. A task with just core gets filesystem, git, system, and other foundational tools.

Every tool has a namespace (the group: filesystem, git, slack) and an access level (read or write). When a trait grants read-only access to a namespace, only read tools from that namespace are available.

III · How It Works

The Flow

When a prompt runs for a task, the MCP server enforces everything. Scroll through each stage:

A task is created with traits like "core" and "debug", and optionally a scope with deny patterns. These are stored in the database.

When a prompt runs, the MCP server looks up the task’s traits and scope from the database. This happens on every session init.

Traits resolve to namespaces. core grants filesystem, git, system, and more at readwrite. debug grants sentry and datadog at read. Scope restrictions — denied tools, access downgrades — are applied on top.

Only allowed tools are registered for this MCP session. Everything else doesn’t exist. The agent can’t even see tools it isn’t allowed to use.

The agent connects and sees only the tools registered for its session. Unregistered tools don’t exist — the MCP SDK rejects calls to unknown tools before our code even runs.

IV · In Practice

A Concrete Example

A task with traits ["core", "debug"] and scope { access: { git: "read" } }.

All Agent IO Is Observable

Because the container has no direct outside access, everything flows through MCP tools

Every single thing the agent does goes through an MCP tool call. Every tool call is logged. There are no side channels — no sneaky curl to an external API, no writing to a file the host reads. If the agent did it, we can see it in the logs.

Adding a new tool? Define it with a namespace and access level. It automatically becomes available to any task with a matching trait. Adding a new trait? Create a row in the database. No code changes needed.

V · Glossary

Terms

Agent Trait

Named capability granted to a task. Defines which tools are available and at what access level.

Agent Scope

Restrictions on capabilities. Can only take away what traits have granted.

Tool Namespace

The group a tool belongs to (filesystem, git, sentry). Traits grant access at this level.

Tool Access

Whether a tool is read (observes) or write (modifies). Read-mode traits only get read tools.

Toolset

The filtered set of tools provided to the agent for a given session.

Denied Tools

Tools excluded by scope — never registered, never visible to the agent.
